# v0.4 模型、侦察与行动规则

水动力及疏散计算沿用 v0.3 冻结结果；v0.4增加侦察、相机和资源行动。

原生0.4 m水文调整DEM独立平均为4 m，再进入求解网格。真实建筑轮廓使用有限高度的等效抬高床面，楼层 / 屋顶高度为示意。桥涵、窄巷、门窗、路缘及地下空间未完整解析。

历史试算以源时间为UTC的2012-06-29 04:30–10:30窗口驱动。rg5427（23.60064 mm）保留为对照，未与rg5425混用。源事件文件省略的分钟按干时段处理；分钟体积解释为该时间戳开始的60秒雨量。每个数值时间步都按累计曲线精确积分，而不是在长时间步中抽取单个雨强。

历史水深不是历史实测积水，常河道边界及初始条件是假设；无入渗 / 无排水使它属于敏感性试算，不能称为已验证灾害重建。初始干区新增湿面积包含边界初始调整影响，不能全部解释为降雨单一因果贡献。

## 展示场与视觉时间

两组均采用201×201节点、8 m展示采样。`*-fields.bin`为小端float32，维度为[帧,40401节点,4]，分量依次为水位m DVR90、水深m、向东m/s、向北m/s。行北→南，列西→东。配套ground为float32，building mask为uint8。

湿邻元局部插值得到展示水位，建筑内部隐藏水面由邻近湿街道补齐。展示插值不守恒，体积及面积使用原生单元统计。水面仅加0.018 m显示偏移；波纹只改变法线，反射为程序化天空近似。

水流粒子采用RK2，南向速度为负的北向速度，浅水 / 建筑 / 低速 / 域外遮罩。视觉平流倍率8×，不代表漂浮物。雨滴采用饱和密度映射，最多900条细线、不透明度不超过约0.30；默认55%密度预算。雨势、累计量由物理时间决定，雨滴和波纹相位可在暂停时继续。

## 风险分区

100×100个16 m户外单元，每分钟分档；覆盖当前至未来30分钟，额外含一分钟保守缓冲及输出帧包络：

- 绿色候选安全：整段预测水深<0.08 m、速度<0.25 m/s；90 m内存在可通过干道路连接的集结点。
- 红色模型危险：水深≥0.30 m，或水深>0.05 m且速度≥1 m/s / 深速乘积≥0.15 m²/s。
- 黄色：有水影响、连通不确定或需核查。
- 灰色：建筑室内、无可确认道路通达或模型域外等未评估区域。

阈值是演示规则，不是官方安全标准。源道路拓扑未核验桥面、交通限制和真实现场适宜性；绿色不代表经现场验证的安全承诺。

## 人员、集结点与巡检

18个假设队列，每组20人，共360人，投放于源道路节点。集结点3处，容量分别160、140、140人，位置及容量是假设。路径规划有10分钟水情前视，每段道路按实际预计通过时刻复核；示意步行规则为水深<0.15 m且速度<0.5 m/s，不满足时重规划或受阻待援。

在途人数预留容量，到达后转为占用。待疏散+途中+到达+受阻始终为360；巡检另计6人。轨迹记录道路转角的精确时间，前端纯按物理时间采样，暂停和倒放不会暗中推进。

3队巡检各2人，在整个计算窗口保持干燥的源道路上往返，含边界检查45秒和集结点引导90秒驻留。只有移动队列与相同目标的引导队在模拟中距离≤45 m时记录引导交接，人物以举臂符号表达引导。角色适度放大用于可视识别；没有真实人口、救援或行为校准。

## 模拟无人机与场景相机

六架无人机使用稳定ID D01–D06，分别执行边界测绘、深水监视、积水点检查、建筑巡查、区域普查和通信中继。观察点按各情景的实际模型水深、孤立湿单元、建筑与集结点确定。离地高度、路径、电量和链路为确定性的演示设定，不是设备遥测、适航或续航论证。

相机与主视图共用同一场景、模型时刻及一个WebGL渲染器，通过视口 / 裁剪绘制画中画或全屏：

- EO：程序化城市与水面场景，不是航拍录像。
- 模型水深：读取当前水场；Ironbow / White hot仅为色板。按观察点自动取1–14 m（历史情景最高2 m）显示范围，色标明确标注米。建筑露出水面的部分保持较暗。
- 模型风险：读取与疏散页面相同的分钟风险单元，包含30分钟前视规则；不是实时设备识别。
- HUD：离地高度m AGL、地速m/s、北向顺时针航向、电量%、链路dBm、相机倍率，以及地面准星的投影坐标 / 高程 / 模型水深。准星高程采样地面，不是屋面测量。

云台、变焦或色板不推进模型时间。EO / 分析切换、全屏放大与还原保持对象和中心观察方向。记录列表是候选点达到模型水深阈值后保存的采样记录，包含来源无人机、坐标、时间和水深；没有影像识别或热成像测温。点击记录会定位模型时刻与实际记录位置。

## 十三个资源与物资守恒

H01–H02直升机、B01–B02舟艇、V01–V03车辆、T01–T03共享巡检队、G01–G02救援队、S01补给站。行动人员共30人，含原有巡检6人，与360名疏散群众分开计数；巡检轨迹和身份在两个工作空间共享。

车辆与地面救援队沿源道路拓扑行进，每段按预计经过时刻检查模型水深<0.15 m且速度<0.5 m/s。运输车使用全窗口干燥的候选路径；V03尝试进入受淹路段并在越过阈值之前停止，日志记录受阻。此后驻点是否继续受淹仍由当前水场显示，停止不等于安全承诺。

舟艇使用连通模型水格，要求任务窗口内水深≥0.4 m、速度≤2 m/s、排除建筑遮罩。规划时使用输出帧包络，验证另以约2 m间距采样实际经过时刻。无满足条件的水路时显示待命及原因；没有真实航道、桥下净空、码头或适航核验。

直升机沿示意航迹投送，不做真实航空调度。物资单位为示意“箱”，补给站初始6,000箱：

- 装载 / 补给期间，库存逐步转移到单位载荷。
- 投送期间，单位载荷逐步减少、累计投送增加；场景显示下降的物资符号，完成后留下落点符号。
- 任意回放时刻：**累计装载 = 累计投送 + 机载 / 车载余量**；**补给站库存 + 累计装载 = 6,000**。
- 两情景窗口末均累计装载560箱、投送330箱、单位余量230箱、站内库存5,440箱。

物资符号代表批次，不要求每箱绘制一个实体。任务、库存和所有行动轨迹均为示意；投送没有修改ANUGA水场，没有启泵、改闸或地表—管网耦合效果。

## 行动数据接口

`*-missions.json`含`schemaVersion:1`、模型ID、时长、假设、无人机、资源、事件和采样记录。模型ID须与当前水动力元数据一致。坐标为相对`city.origin`的东 / 南向米制坐标，垂直基准DVR90，AGL相对展示地面。

轨迹行是`[模型秒, 东向x, 南向z, 离地高度m, 状态, 载荷箱数]`。状态与位置由当前模型时间二分查找；区间内位置、离地高度和载荷连续插值，状态在时间节点切换。记录只在相应时刻出现，倒拖会恢复之前的余量、库存与日志。

`mission-core.js`提供纯函数采样；`mission-view.js`消费同一结果绘制实体和落点；`flight-camera.js`读取当前场景和水场；工作空间面板与图表使用相同对象ID。快照导出包含模型、物理时间、当前任务、遥测、资源余量、事件、相机、坐标原点、坐标系和单位。

大型水场按需加载，激活后只保留一个情景的场数组；加载切换阶段允许旧 / 新数组短暂并存。场景几何和纹理存储复用，换情景清理旧任务模型、路径与派生曲线。窄屏相机打开时自动定位地图，云台与控件保持在区域内。加载失败保留原情景并允许重试；首次加载失败时禁用尚不可用的控制，仅保留重试入口。

## 回放与演示导览

物理时间控制水情、人员、任务、遥测、库存和累计量。1×为每秒推进60模型秒，0.25×为每秒15模型秒。暂停后这些状态固定；视觉雨滴、水纹、示踪粒子和相机过渡可继续。全景环绕属于视图操作，不改变业务数据。

26段导览把参考视频流程映射到当前洪涝情景。单段选择暂停以便检查；自动导览按参考片段时长切换，并以0.25×推进片段内的动作。暂停 / 结束导览停止其时间推进；手动切换工作空间或拖动时间退出导览。参考中的风流线对应本项目的求解水流方向，热成像对应有单位的模型分析色板。

## 复现

浏览器回放使用仓库内冻结数据。完整数值复现依赖原始Bellinge输入和独立数值环境。可配置`FLOODTRACE_DATA_ROOT`及`FLOODTRACE_PYTHON`后运行根目录`reproduce.sh`。两引擎始终使用不同可执行进程。实际依赖版本记录在`numerical-environment.txt`，本机原生库设置不作为跨平台自动安装保证。
